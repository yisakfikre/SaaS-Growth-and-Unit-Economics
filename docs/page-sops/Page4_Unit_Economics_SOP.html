0.2 — Flow vs snapshot: which measures the Period window applies to

This distinction governs every DAX decision below. Flow measures accumulate activity over a span and are meaningful to sum across months. Snapshot measures describe a state at a point in time and were never summable.

MeasureTypePeriod window?
Marketing SpendFlowYes
LeadsFlowYes
_New Customers by ChannelFlowYes
Lead to Customer Conversion RateFlow ÷ FlowYes — both terms, same window
Blended Marketing CACFlow ÷ FlowYes — both terms, same window
ARPASnapshotNo
Logo Churn RateSnapshotNo
Estimated LTVSnapshot (built from ARPA + churn)No
Estimated LTV to CAC RatioSnapshot ÷ windowed flowInherits from CAC only
Marketing CAC Payback (Months)Windowed flow ÷ snapshotInherits from CAC only
The mixed ratios are intentional, not an inconsistency
Estimated LTV to CAC Ratio and Marketing CAC Payback (Months) each combine a snapshot term with a windowed-flow term. That is standard SaaS unit-economics practice: LTV is the forward-looking value of today's customer relationship; CAC is the trailing cost of acquiring customers over a recent window. Do not "harmonize" them.

0.5 — Period Options mechanism NEW

Disconnected lookup table, no relationship to anything — the same mechanism already proven in this model for Assumed Gross Margin %.

  1. Home ribbon → Enter data. Column Period, one row: Last 12 complete months. Table name: Period Options → Load.
  2. Create no relationship from this table to DimDate or anything else.
_P4 Period Start Date = 
VAR SelectedPeriod = SELECTEDVALUE ( 'Period Options'[Period], "Last 12 complete months" )
VAR PeriodEndDate = EOMONTH ( MAX ( DimDate[Date] ), 0 )
RETURN
SWITCH (
    SelectedPeriod,
    "Last 12 complete months", EOMONTH ( PeriodEndDate, -12 ) + 1,
    EOMONTH ( PeriodEndDate, -12 ) + 1
)
_P4 Period End Date = EOMONTH ( MAX ( DimDate[Date] ), 0 )
Only one option is approved
"Last 12 complete months" is the only period option confirmed anywhere in this project's sources. Do not invent others. If more are approved later, add rows to the Period Options table and extend the SWITCH — no structural change required.

0.6 — New measures NEW

_New Customers by Channel = SUM ( FactMarketing[NewCustomers] )

Genuinely new — [New Customers] is a different concept (distinct customer entities from FactSubscriptionEvent, company-wide) and is load-bearing on Page 3. These two can legitimately disagree; that is expected, not an error.

Applying the Period window. Use this pattern only for measures classified as shape B in 0.3, and for _New Customers by Channel:

<measure> = 
CALCULATE (
    <existing aggregation>,
    FILTER (
        ALL ( DimDate ),
        DimDate[Date] >= [_P4 Period Start Date] &&
        DimDate[Date] <= [_P4 Period End Date]
    )
)

For shape A measures, do not modify the measure at all — instead apply the window once at page level in 0.7.

P4 Blended CAC (All Channels) = 
CALCULATE ( [Blended Marketing CAC], REMOVEFILTERS ( 'DimAcquisitionChannel' ) )

0.7 — Page-level period filter (shape A route only)

If the base flow measures proved to be plain sums with no internal date logic, apply the Period window once rather than editing six measures:

  1. With no visual selected, Filters pane → Filters on this page.
  2. Drag DimDate[Date] in → Filter type: Advanced filtering.
  3. Bind via fx to [_P4 Period Start Date] / [_P4 Period End Date] if your build supports measure-bound advanced filters. If it does not, fall back to modifying the flow measures individually per 0.6 — and note that choice in the build log so a future reader knows why.
Why the page-level route is preferable when available
It leaves every existing measure definition untouched, which means nothing can regress on any other page, and the Period selector governs the whole page with one object instead of six near-identical edits.
