0.2 — Missing measures to create before building new

All are mechanical derivations of locked measures — no new business logic, no change to any approved definition. Add all to _Measures.

Gross New MRR = [New MRR] + [Expansion MRR]
_Gross New MRR Split Text = 
VAR Gross = [Gross New MRR]
RETURN
FORMAT ( DIVIDE ( [New MRR], Gross ), "0%" ) & " / " &
FORMAT ( DIVIDE ( [Expansion MRR], Gross ), "0%" )
_Net MRR Change Delta Value = 
VAR Current = [Net MRR Change]
VAR Prior = CALCULATE ( [Net MRR Change], DATEADD ( DimDate[Date], -1, MONTH ) )
VAR d = Current - Prior
RETURN IF ( d >= 0, "▲ +", "▼ " ) & FORMAT ( ABS ( d ), "$#,##0,.0K" )
_Net MRR Change Delta Color = 
VAR Current = [Net MRR Change]
VAR Prior = CALCULATE ( [Net MRR Change], DATEADD ( DimDate[Date], -1, MONTH ) )
RETURN IF ( Current - Prior >= 0, "#16A34A", IF ( Current - Prior < 0, "#DC2626", "#94A3B8" ) )
_MRR by Plan MoM Delta = 
VAR Current = [_MRR by Plan]
VAR Prior = CALCULATE ( [_MRR by Plan], DATEADD ( DimDate[Date], -1, MONTH ) )
RETURN DIVIDE ( Current - Prior, Prior )
_MRR by Plan MoM Delta Color = 
IF ( [_MRR by Plan MoM Delta] >= 0, "#16A34A",
     IF ( [_MRR by Plan MoM Delta] < 0, "#DC2626", "#94A3B8" ) )
0.3 — Verify [New MRR] before building the composition chart
[New MRR] was flagged during the Page 1 build as a likely carrier of the unscoped-SUM bug (a bare CALCULATE with only an EventType filter and no date restriction) but was never confirmed, because the waterfall fix routed around needing it. It is now load-bearing twice over — in Gross New MRR above and in the composition chart's stack.

Check it now: open [New MRR] in the formula bar. If it reads CALCULATE ( SUM ( FactSubscriptionEvent[MRRChange] ), FactSubscriptionEvent[EventType] = "New" ) with no date filter, apply the same fix already used on Expansion/Contraction/Churned MRR: 
New MRR = 
VAR CurrentPeriodEnd = MAX ( DimDate[Date] )
VAR CurrentYear = YEAR ( CurrentPeriodEnd )
VAR CurrentMonth = MONTH ( CurrentPeriodEnd )
RETURN
CALCULATE (
    SUM ( FactSubscriptionEvent[MRRChange] ),
    FactSubscriptionEvent[EventType] = "New",
    FILTER ( ALL ( DimDate ), YEAR ( DimDate[Date] ) = CurrentYear && MONTH ( DimDate[Date] ) = CurrentMonth )
)
Validate: with no filters, [New MRR] must return $38,504.60 (Dec 2025). If it returns something in the millions, it was unfixed.
0.4 — _MRR by Plan % of Total must be replaced for the field parameter
The existing measure hard-codes ALL ( DimPlan ): 
 _MRR by Plan % of Total = DIVIDE ( [_MRR by Plan], CALCULATE ( [_MRR by Plan], ALL ( DimPlan ) ) )
That is correct while the matrix shows Plan, but returns wrong shares the moment the field parameter switches the row axis to CustomerSegment — ALL(DimPlan) does not clear a DimCustomer filter, so the denominator stays plan-scoped. Create this parameter-safe version and use it in the matrix instead (leave the original alone; Page 1's bar chart still uses it): 
_MRR Share of Total = 
DIVIDE ( [_MRR by Plan], CALCULATE ( [_MRR by Plan], ALLSELECTED () ) )
ALLSELECTED() removes row-level axis filters from whichever dimension the parameter is currently projecting, while respecting slicer selections — so the shares always sum to 100% on both Plan and Segment.
0.5 — BLOCKER: plan cross-filtering (spec Section 11) cannot work as written
The approved spec requires: "selecting a plan bar filters all three charts." Against the current locked model this is not implementable for Plan, and the reason is structural, not a formatting setting:

DimPlan has exactly one active relationship in the model — to FactSubscription. The combo chart ([MRR], [MRR Growth %]), the waterfall (_MRR Change (Current Month)) and the composition chart ([New MRR] etc.) are all built from FactSubscriptionEvent, which has no active relationship to DimPlan — NewPlanID and PreviousPlanID were both deliberately deactivated in Phase 3 to prevent blank-row contamination, and are only reached via USERELATIONSHIP inside specific churn measures. Setting Edit interactions to Filter will not help: there is no path for the filter to travel. This is the identical limitation already documented and accepted on Page 1 (MRR by Plan does not cross-filter that page).

What DOES work: when the field parameter is switched to Segment, cross-filtering works on all three charts — DimCustomer has active relationships to both fact tables. So the requirement is half-satisfiable as written.

Implement as: Section 11 below sets the matrix→charts interactions to Filter. On Segment they will filter correctly; on Plan they will not respond. Do not treat the non-response as a build error. Resolving it properly means rebuilding the core measures onto FactSubscription or adding an EffectivePlanID column to FactSubscriptionEvent — both reopen Phase 2/3, which this SOP is instructed not to do. Flag in template notes.

    Corrected three times during the build — the reasoning matters more than the number. It originally read "leave blank (auto)", which breaks on any dataset whose early months start from a small base: MRR here begins at $18.9K, so early-2023 months post growth rates near 50%, the auto axis stretches to fit them, and all later months compress into unreadable slivers — the chart then falsely reads "growth was enormous once and stopped". What a matrix can and cannot reproduce from the mockup
The approved design was drawn in HTML, where a row can stack a value above a full-width bar with a gray track behind it. A Power BI matrix gives every measure its own side-by-side column — that is what a matrix is. Two things in the mockup therefore have no native equivalent and should not be chased: (1) value-and-share stacked above a full-width bar, and (2) the light gray 100% track behind each bar. The formatting below gets everything else. Rebuilding this as layered bar-chart-plus-text-cards would take 15+ visuals per card, be fragile to maintain, and break the Top-N reusability the spec requires — not worth it for a cosmetic gain.

Format

  1. Format visual → General → Properties → X=856, Y=430, Width=408, Height=274.
  2. Format visual → Visual → Values → Font: Segoe UI, Size 10, Color #0F172A.
  3. Values → Alternate background color: set to #FFFFFF (or toggle the alternating row style off). Zebra striping is not in the approved design.
  4. Values → Row padding: set so rows render at 31 px. Increase/decrease padding and re-measure; the fixed height prevents a wrapping category name from pushing the footer out of the card.
  5. Format visual → Visual → Row headers → Font Size 10, Color #0F172A, Alignment: Right (matches the design — labels sit against the bars).
  6. Row headers → Word wrap: Off. This produces the ellipsis truncation the spec requires and protects the 31px row height.
  7. Format visual → Visual → Column headers: Off. The subtitle already carries the labeling and the design shows no column header row. If you prefer to keep the "Δ MoM" label visible, leave headers On and instead use Rename for this visual on the two MRR columns to blank them out.
  8. Format visual → Visual → Gridlines → Vertical: Off. Horizontal: Off.
  9. Format visual → Visual → Totals → Row subtotals: On. Set its Label to Total MRR. Font: Semibold. (The design's dynamic "· 5 of 5 plans shown" suffix would need its own measure — optional, not built here.)
  10. Format visual → General → Title → Text: Revenue composition, Size 14 Semibold.
  11. Format visual → General → Subtitle → Text: MRR · share of total, Size 10, Color #94A3B8.

Conditional formatting — data bars on MRR

Do not use #0F1B3D here — at navy the bar and the dark value text render at nearly the same darkness and the largest row's figure becomes unreadable on top of its own bar.
