## Analytical limitations

### The data is synthetic

Generated by a seeded Python simulation, 2023-01-01 → 2025-12-31. **No figure describes a real business.** Churn is driven by a tenure-based hazard function, segment, plan tier and a probabilistic health-score link, plus three simulated soft-economy months. 57 small data-quality issues are seeded deliberately for Power Query cleanup practice; none break referential integrity.

Patterns in this data are *emergent from the simulation*, not hardcoded — but they are still properties of a simulation.

### ⚠️ LTV, and every ratio built on it

`Estimated LTV = ARPA × Assumed Gross Margin % ÷ smoothed monthly revenue churn rate`

This is the standard simplification and it inherits two well-known weaknesses:

1. **It assumes a constant churn rate forever.** This report's own cohort curve disproves that assumption on its own data — churn is front-loaded (88.78% retained at 3 months) then flattens (61.05% at 30). A single smoothed rate understates early loss and overstates late survival.
2. **A small denominator makes the output unstable.** On this dataset's low revenue churn, blended LTV:CAC computes to **35.7×**.

**35.7× is not a SaaS benchmark. It is what this formula returns on this data.** The conventional 3× rule of thumb applies to differently-constructed LTV figures and does not transfer. Page 4's 50× default target reflects the formula's scale on this dataset, not any industry standard.

**Use LTV:CAC here as a relative ranking across channels** — defensible, because every channel runs through the same formula with its own ARPA and churn — **and not as an absolute number.**

### CAC is marketing-only

`Marketing CAC` = marketing spend ÷ new customers. It excludes sales salaries, commissions, onboarding costs and overhead. Fully-loaded CAC would be materially higher. The page titles say "Marketing CAC" rather than "CAC" for exactly this reason.

### Association, never causation

`ChurnReason` records a category someone selected at cancellation. It does not establish why the customer left, and "Lack of Usage" being largest by churned MRR does not mean usage caused the churn. Health scores correlate with churn *by construction* in the simulation.

### Health-at-churn has a resolution limit

Snapshots are captured roughly quarterly, so "last value before churn" can be up to several months stale relative to the actual churn date. The 54.71 figure is a real average of real last-observed values; it is **not** a reading taken on the day someone left. The page states this on itself.

### ARR is a run-rate

`ARR = MRR × 12` annualises the current month. It will not tie to a trailing-twelve-month revenue total and is not meant to.

## Structural limitations

| Limitation | Consequence |
| --- | --- |
| **`FactMarketing` has no customer or segment dimension** — it is channel × month grain | Page 4's Segment slicer is present for cross-page visual consistency but does not filter channel-level marketing metrics |
| **`FactSubscriptionEvent` carries two plan keys** (`NewPlanID`, `PreviousPlanID`) | Neither relationship to `DimPlan` can be active. Every plan-level measure on event data needs `USERELATIONSHIP` |
| **Native Top-N never creates an "Other" bucket**, in any Power BI visual type | A true "Other" requires a custom rank-and-relabel column, which is what `DimAcquisitionChannel[Channel Group]` does |
| **No measure-based filter can exist at page or report level** — visual level only | Page 4's Top-N cutoff is applied to three visuals individually and synchronised by hand |
| **Plans carry MRR but not customer counts** | A customer moves between plans over their lifetime, so plan-level *customer* attribution needs a point-in-time choice the report declines to make implicitly. Page 6 therefore shows churned **MRR** by plan, not a plan-level churn rate |

## Accepted design decisions

Deliberate, with the trade-off stated.

| Decision | Trade-off accepted |
| --- | --- |
| **Page 4 uses a discrete "Last 12 complete months" selector** rather than the continuous date slider on every other page | Inconsistent with the other five pages, deliberately — CAC and payback are meaningless at a single-month grain. The fuller intended option list beyond this single default was never specified |
| **Three-visual KPI card construction** (value + delta + caption) instead of one Card visual | Higher object count and slower page loads, in exchange for correctness — Card (new)'s reference-label conditional formatting was unreliable. Re-examined during performance work and kept |
| **Page 6's cohort heatmap keeps visible cell values** on top of the colour gradient | 2,457 ms render — the single largest visual cost in the report. Colour carries direction, numbers carry precision; both judged to earn their place |
| **Page 4's Channel Detail sorts by its visible LTV:CAC column**, not a hidden sort key | "Other" sorts wherever its value places it rather than being pinned last |
| **Short-label abbreviations are hand-picked** for Segment and Plan | A named exception to the no-hardcoded-category-text rule, with a `SWITCH` fallback for unseen names |
| **Cohort heatmap does not participate in cross-filtering** | A longitudinal question; cross-filtering it by a calendar-month selection would misrepresent it. Noted so it reads as intentional |
| **`Channel Group` is a calculated column** | Ranks channels as of the last model refresh rather than the current Period selection. Correct for a stable "Other" label; worth knowing before relying on it under a narrowed period |

## Deferred work

Scoped and deliberately not built. These are future work, not oversights.

| Item | State |

| **Replacement-data testing at a different category count** | A fourth segment or sixth plan was never tested — it would require genuinely new data, judged disproportionate to simulate pre-emptively rather than at the point a real client needs it |

## Open items

Unresolved. Listed rather than quietly closed.

### Pages 1–2 "Top N + Other" — not re-checked

Both pages were specified as "Top N + Other" **before** it was established that native Top-N never creates an "Other" bucket. Page 4 was re-checked and corrected. **Pages 1–2 were not.** It is entirely possible one or both carry the same silent gap Page 4 had.

### Page 5 share re-summing — untested

`_MRR Share of Total` was validated against Page 2's two-option field parameter. Page 5's three-option parameter is untested. The specific open check: select one group on Page 5, add the five plan share percentages by hand, confirm they total 100% *within that group* rather than against the company-wide baseline.

### Documentation vs. build: the "Other" bucket

The Step 6 QA record states that exclude-only behaviour (no "Other" row) was accepted as Page 4's final design. **The shipped model contradicts this** — `Channel Group` produces an "Other" bucket and the published Page 4 image shows it. The build moved on and the record was not updated. **The build is correct; the record is stale.** Flagged rather than silently reconciled.

### Page 1's Executive Insight card

A "Net MRR Change" row was flagged during an early audit as potentially restating a KPI already visible on the page. Never actioned — an optional future trim.

### Some measures were never live-confirmed

The measure inventory marks these **Unverified** rather than assuming them correct. See [`qa-records/Phase5_Step1_Measure_Validation.md`](qa-records/Phase5_Step1_Measure_Validation.md).

### Performance cause not conclusively isolated

Cold navigation takes 9.5–14.5 s on heavier pages. Bookmark navigation was ruled out; destination-page visual-object count was confirmed as a driver; memory pressure was identified as plausible but **not proven** with a controlled test. Performance Analyzer logs nothing during the gap, placing the bottleneck below its instrumentation. Accepted rather than solved.

## Maintenance requirements

What someone adopting this template is responsible for. These are normal onboarding duties, not defects.

1. **Synchronise the Page 4 Top-N cutoff by hand** across all three affected visuals — the Channel Economics scatter, the Channel Detail table, and the Where Spend Sits panel — if it is ever changed from 6. Nothing enforces this automatically, and a mismatch produces three visuals that quietly disagree.
2. **Set the three Unit Economics parameters for every new client** — Assumed Gross Margin %, LTV:CAC Target, Minimum Volume Threshold. They ship with illustrative defaults (80% / 50× / 30 customers), not neutral ones.
3. **Replace `[Company Name]`** in the header on all six pages.
4. **Confirm the source file matches the documented contract** before first load — sheet names, column names, and the content rules in [SETUP.md](SETUP.md#non-negotiable-content-rules). The `MRRChange` sign convention is the one that silently produces wrong numbers rather than an error.
5. **Use `USERELATIONSHIP` for any new plan-level measure** written against `FactSubscriptionEvent`. Without it, the measure returns unfiltered totals that look plausible.
6. **Revert `SourceFilePath` exactly** if you ever change it for testing. A near-miss path caused a multi-hour debugging session during validation — the model was loading a different file, perfectly correctly.
