Step 6 — MRR Movement (waterfall)

  1. Insert → Waterfall chart. Format → General → Properties: X=856, Y=302, Width=408, Height=220.
  2. Category: a small disconnected table or the four category labels "New", "Expansion", "Contraction", "Churned" — build via a category column if not already present from Phase 3, or use Breakdown with Subscription_Events[EventType] filtered to those four values only (already validated no other event types exist).
  3. The category axis defaults to alphabetical order — "Churn" sorts before "Contraction," breaking the intended New → Expansion → Contraction → Churned narrative flow. Add a small sort-order column: 
    EventTypeSortOrder = SWITCH ( FactSubscriptionEvent[EventType], "New", 1, "Expansion", 2, "Contraction", 3, "Churn", 4, 99 )
    Then Modeling ribbon → select EventType → Sort by column → EventTypeSortOrder. This is a calculated column — a bigger category of change than the measures elsewhere in this SOP — but a static 4-value mapping with no interpretive judgment involved, unlike the Customer Health banding decision flagged in Step 11.
  4. Y-axis / Values: add this new measure, not a raw column and not [New MRR]/[Expansion MRR]/[Contraction MRR]/[Churned MRR] individually. A plain "Sum of MRRChange" has no date-scoping and will sum across whatever the Period slicer's whole window is, not one month. The four named category measures won't work either, for a different reason: each hard-codes its own EventType filter internally, which overrides the ambient category context this visual relies on — every bar would end up showing the same one category's figure. This measure restricts the date only, deliberately leaving EventType untouched so the waterfall's own category breakdown flows through correctly: 
    _MRR Change (Current Month) = 
VAR CurrentPeriodEnd = MAX ( DimDate[Date] )
VAR CurrentYear = YEAR ( CurrentPeriodEnd )
VAR CurrentMonth = MONTH ( CurrentPeriodEnd )
RETURN
CALCULATE (
    SUM ( FactSubscriptionEvent[MRRChange] ),
    FILTER (
        ALL ( DimDate ),
        YEAR ( DimDate[Date] ) = CurrentYear &&
        MONTH ( DimDate[Date] ) = CurrentMonth
    )
)
  5. Format → Sentiment colors: Increase #16A34A, Decrease #DC2626, Total #0F1B3D.
  6. Turn on the waterfall's built-in "Show total" option — its value should match [Net MRR Change] exactly. Its label, however, will render as "Total" and can't be renamed through the Format pane — this is a confirmed, long-standing Power BI limitation (open on Microsoft's own ideas forum for years), not a setting you're missing. Cover it with a text box: insert a text box reading "Net change", solid white fill (not transparent — you're occluding the native text, not replacing it), styled to match the other four category labels, positioned directly over where "Total" renders. Group it with the waterfall so it moves as one unit.
  7. Bar width ~56px (Format → Layout → gap width, adjust to approximate). Labels above bars on. No gridlines. Add a "$ thousands" note as a small text box under the axis instead of per-label units, per the number-format hierarchy rule.
  8. Title "MRR Movement", subtitle showing the current month (e.g. "Dec 2025"), 14px/10px per the same title-zone treatment as Step 5.

Step 8 — MRR by Plan

Corrected after build feedback
Two fixes to the original version of this step: (1) [MRR] is built from FactSubscriptionEvent, which has no relationship path to DimPlan — it can't be filtered by plan at all and will show the same grand-total on every bar. Use _MRR by Plan instead (built on FactSubscription, which does relate to DimPlan). (2) "Show value as → Percent of grand total" only works cleanly on a table/matrix; on a Clustered Bar Chart, a second field in Values creates a second clustered bar per category, not a combined label. Use an explicit percentage measure instead.
  1. Add the measure, if not already built from the earlier relationship fix: 
    _MRR by Plan = 
VAR CurrentDate = MAX ( DimDate[Date] )
RETURN
CALCULATE (
    SUM ( FactSubscription[MonthlyPrice] ),
    FactSubscription[StartDate] <= CurrentDate,
    FactSubscription[EndDate] > CurrentDate || ISBLANK ( FactSubscription[EndDate] )
)
  2. Add the percentage measure: 
    _MRR by Plan % of Total = 
DIVIDE ( [_MRR by Plan], CALCULATE ( [_MRR by Plan], ALL ( DimPlan ) ) )
  3. Insert → Bar chart (horizontal). X=436, Y=534, W=408, H=170.
  4. Axis: DimPlan[PlanName]. Values: _MRR by Plan only — a single field, so the chart stays one bar per plan with no clustering.
  5. Sort descending by _MRR by Plan.
  6. Format → Bars: 14px thickness, track color #F4F5F7 behind each bar (Format → Bar background if your version supports it, or approximate with a light gridline-only backdrop).
  7. Remove the x-axis. For the data label, check whether Format → Data labels in your version lets you point the displayed text at a different field than the one plotted — if so, build _MRR by Plan Label = FORMAT([_MRR by Plan],"$#,##0,K") & " · " & FORMAT([_MRR by Plan % of Total],"0%") and use that as the label source, giving a single combined "$186K · 38%" style label per bar. If your version doesn't expose that option, the reliable fallback is: leave the data label as the plain dollar value, and add _MRR by Plan % of Total to the Tooltips well instead, so it shows on hover rather than persistently — a small, deliberate deviation from "value + % printed at row end" worth confirming is acceptable before settling on it.
  8. Top N filter: Filters pane → Filter type "Top N" → 5 by _MRR by Plan, with "Include Other group" on if your version supports it. With exactly 5 plans in the model, Top 5 shows all of them and "Other" will simply never appear — that's expected, not a bug; the filter exists so this template still works if a future deployment has more plan tiers.

Step 10 — Header slicers: Period + Segment

Corrected twice after build feedback — settled here
The plain "Relative Date" style anchors to the real system clock: today's real date is well past this dataset's Dec 2025 end, so "Last 36 Months" on that style currently shows a shrunk window missing Jan–Aug 2023. The "Date picker" style was expected to fix this via an anchor-to-last-date option, per Microsoft's documentation — but in this build, Date picker's actual UI exposes only manual Start date / End date fields, no relative configuration and no anchor option, confirmed by checking both the Format pane and the on-visual corner dropdown. Since this dataset is a fixed 3-year snapshot that will never extend past Dec 2025, a manually fixed range is the correct, permanent answer here — not a workaround.

Prerequisite — Date picker is a preview feature, off by default: File → Options and settings → Options → Preview features (left-hand list, Global section) → check Date picker slicer → OK → restart Power BI Desktop and reopen this file. If Date picker never appears in the Style dropdown below, this is almost always why.

  1. Insert → Slicer. Drag DimDate[Date] into its field well (not a Date Hierarchy — click the field's chevron and select the plain date column if a hierarchy gets added automatically).
  2. Format → Slicer settings → Options → Style: select Date picker. Set Start date = January 1, 2023 and End date = December 31, 2025 — a fixed range matching the dataset's actual full span exactly. No relative or anchor configuration needed for this dataset.
  3. Format → General → Properties: X=1066, Y=20, Width=180, Height=28, in the header band's right side.
  4. Insert a second Slicer. Drag DimCustomer[CustomerSegment] into its field well. Format → Slicer settings → Options → Style: Dropdown. Leave no pre-selected value so it defaults to showing "All."
  5. Position immediately right of the Period slicer, height 28px, sized to fit comfortably without overlapping the Filters button area built in Step 11.
  6. Style both slicers: Format → Slicer settings → Background off, Border off — so they sit directly on the header rather than showing their own box. Text formatting: 11px, #64748B.
Flag for Phase 5 template documentation
This fixed range won't automatically follow a different, live-refreshing dataset if this template is ever reused elsewhere — whoever reuses it needs to manually update these two dates to match their source's actual range. Note this explicitly in the Phase 5 data-contract documentation; don't leave it to be rediscovered.

Step 12 — Cross-filter interactions

Corrected after build feedback
Two of the interactions below turned out not to be available the way the original design assumed, for reasons specific to this model, not bugs: DimPlan has an active relationship only to FactSubscription, so MRR by Plan has no path to filter anything built from FactSubscriptionEvent (which is everything else on this page) — cross-filtering it broadly would require rebuilding several measures to route through FactSubscription, decided against for now. Separately, [Active Customers] hard-codes an EventType filter internally (via its two component measures), which makes it structurally unreachable by the waterfall's own EventType-based cross-filter — a genuine DAX filter-precedence effect, not a relationship gap, and there's no single obviously-correct number "Active Customers filtered to Churn events only" would represent anyway.
  1. Select the MRR by Plan bar → Format → Edit interactions → set its effect on MRR Trend, Active Customers Trend, and all four Tier 2 cards to None. This isn't a workaround — there's no relationship path for it to filter through regardless of this setting, so None simply makes that explicit rather than leaving it as an unexplained accident.   2. Select the MRR Movement waterfall → Format → Edit interactions → confirm its effect is Filter on MRR Trend and all four Tier 2 cards (this already works correctly).
